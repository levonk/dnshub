# PRD: DNS Orchestrator (Rust)

**Status:** Implemented — all 35 stories across Phases 01-06 merged into main (843 tests passing)
**Date:** 2026-08-10
**Service slug:** `dnshub`
**Service name:** `dnshub`

## 1. Problem Statement

The current DNS stack is 9+ services stitched together with 4 config formats
across 4+ IP addresses in a chain:

```
nftables → AdGuard Home → dnsdist → CoreDNS → Unbound → dnscrypt-proxy → Tor → keepalived
```

Each service does its job well, but the **glue layer** (blocklists, rate
limiting, ECS stripping, cache, ordered fallback, per-client policy, UI) is
spread across AdGuard + dnsdist + CoreDNS with no single source of truth for
configuration, policy, or observability.

The hard protocol work (DNSSEC validation, ODoH, DNSCrypt, anonymized relays)
lives in Unbound and dnscrypt-proxy — those should stay. The glue should
collapse into one Rust service.

## 2. Goal

Replace AdGuard Home + dnsdist + CoreDNS with a single Rust service that:

1. Serves DNS (UDP/TCP) on port 53
2. Serves DoT (port 853) and DoH (port 443) to LAN clients
3. Serves DHCP — IP lease management, lease table is the source of truth
   for per-client policy (no external dnsmasq needed)
4. Does ad/tracker blocking with categorized blocklists
5. Does security blocklists (malware, phishing) with category metadata
6. Does rate limiting and ECS stripping
7. Serves local zones (Tailscale MagicDNS, internal names)
8. Caches responses with serve-stale (RFC 8767)
9. Orchestrates ordered fallback to upstream tiers (Unbound, dnscrypt-proxy)
10. Applies per-client policy (parents vs kids vs IoT vs guest) — uses DHCP
    lease table for client identification
11. Exports metrics (Prometheus) and structured logs (tracing/JSON → Loki)
12. Stores recent query log in embedded SQLite for TS frontend viewing
    (dual: Loki for long-term/Grafana, SQLite for live TS frontend)
13. Has a TypeScript frontend (NextJS, static export) for config, status,
    and query log viewing
14. Is configured via TOML config files (automation-friendly)

**Non-goals (kept as external services):**

- DNSSEC validation — Unbound handles this (kept)
- ODoH / DNSCrypt / anonymized relays — dnscrypt-proxy handles this (kept)
- Tor transport — Tor SOCKS proxy kept
- keepalived VRRP — kept as sidecar
- Tailscale mesh — kept as-is
- nftables TPROXY — kept on host

## 4. Technical Decisions

### 4.1 DNS framework: hickory-server 0.26

**Decision:** Build on `hickory-server` with a custom `RequestHandler` chain.

**Why:**
- Trait-based composition model — implement `RequestHandler` to intercept
  queries, wrap `Catalog` for zone dispatch
- Built-in: `BlocklistAuthority`, `ForwardAuthority`, local zones, DoT/DoH
  client, `metrics` facade integration
- Missing (must implement custom): rate limiting, per-client policy, tiered
  fallback, ECS stripping, serve-stale
- Maturity: 0.26.1 (May 2026), used by Let's Encrypt and Google Pixel,
  OSTIF security-audited
- Risk: API churn (Authority → ZoneHandler rename in 0.25-0.26), "not for
  production" crates.io warning, UDP drops under load (mitigated by
  SO_REUSEPORT tuning)

**Mitigation:** Pin to 0.26.x, implement missing features as custom
handlers (not forks), performance test before production. Fallback: use
only `hickory-proto` for wire format and build the server from scratch if
hickory-server proves unstable.

**Built-in features used:**
- `BlocklistAuthority` — blocklist lookups (we wrap it for per-client policy)
- `ForwardAuthority` — upstream forwarding (one per tier)
- `InMemoryZoneHandler` / `FileZoneHandler` — local zones
- `CachingClient` — LRU cache with TTL clamping (we add serve-stale wrapper)
- DoT/DoH client — encrypted upstream queries
- `metrics` facade — Prometheus endpoint

**Custom handlers to implement:**
- `RateLimitHandler` — token bucket per source IP
- `PolicyHandler` — per-client profile resolution + blocklist selection
- `EcsStripHandler` — remove EDNS ClientSubnet from responses
- `ServeStaleHandler` — wrap CachingClient, serve expired entries on upstream
  failure (RFC 8767)
- `TieredForwardHandler` — ordered fallback through tier ForwardAuthorities
  with per-tier timeout
- `MetricsHandler` — record per-query metrics (rate, latency, decisions)

### 4.2 Blocklist storage: LMDB via `heed` crate

**Decision:** Use LMDB (via the `heed` crate) for blocklist storage, with a
two-stage Bloom filter front for fast negative answers.

**Why not CDB:**
- The `cdb` Rust crate has been abandoned since 2018
- CDB has no prefix/wildcard matching
- CDB has a 4GB file size limit

**Why LMDB/heed:**
- Actively maintained by Meilisearch team (0.22.1, Apr 2026)
- True mmap — single-level store, OS handles paging, no separate cache
- B-tree with mmap: fast point lookups, supports prefix search via cursor
  (`MDB_SET_RANGE`)
- Atomic file swap for hot-reload (build new file, rename, reopen mmap)
- Typed values: store category bitmap + source list IDs per domain
- ~65% overhead over raw data (vs 300%+ for RocksDB)
- C dependency (LMDB) but well-tested, no Rust safety concerns via heed

**Storage schema:**
```
Key:   reversed domain (e.g., "net.doubleclick.www") — enables prefix search
Value: serialized BlocklistMetadata {
    categories: CategoryBitmap,   // u32 bitmask: ads|tracker|malware|phishing|
                                  //   adult|gambling|social|dating|piracy|
                                  //   streaming|games|fakenews|telemetry
    sources:   u16,                // bitmap of source list IDs
    first_seen: u32,               // unix timestamp
    last_updated: u32,             // unix timestamp
}
```

**Two-stage lookup:**
1. Bloom filter (`fastbloom` crate, ~10-15MB for 1M entries @ 0.1% FPR) —
   if "definitely not blocked", return immediately (fast path for the
   ~99% of queries that are legitimate domains)
2. LMDB lookup — if Bloom says "maybe blocked", confirm in LMDB and
   retrieve category metadata

**Hot-reload:**
1. Background thread downloads + compiles new LMDB file to temp path
2. Atomic rename over old file
3. `ArcSwap` the database handle
4. Old readers continue until dropped (zero-downtime)

### 4.3 Blocklist sources: source-based category tagging

**Decision:** Subscribe to multiple category-specific lists and tag entries
by source list. Domains appearing in multiple lists accumulate categories.

**Why:** Most blocklists are flat (domain present/absent, no per-domain
metadata). The category is implicit from which list the domain came from.

**Default subscription set:**

| Category | Source | Format | Refresh |
|----------|--------|--------|---------|
| Ads | EasyList + EasyPrivacy | Adblock | 4-6 days |
| Ads/Tracking | AdGuard Base + Tracking | Adblock | 4 days |
| Ads/Tracking (baseline) | HaGeZi Normal | Domains | Daily |
| Malware/Phishing | HaGeZi TIF | Domains | 6 hours |
| Malware | URLhaus | CSV/JSON | 15 min |
| Adult | StevenBlack porn + HaGeZi NSFW | Hosts/Domains | Daily |
| Gambling | StevenBlack gambling + HaGeZi Gambling | Hosts/Domains | Daily |
| Social | StevenBlack social | Hosts | Daily |
| Fake News | StevenBlack fakenews | Hosts | Daily |
| Piracy/Streaming/Games/Dating | IPFire DBL category zones | Domains/RPZ | Daily |
| Telemetry | Disconnect.me Analytics | JSON | Daily |

**Category bitmap (u32, 32 categories max):**

| Bit | Category | Description |
|-----|----------|-------------|
| 0 | ads | Advertising |
| 1 | tracker | Tracking / analytics |
| 2 | telemetry | Device telemetry / phoning home |
| 3 | malware | Malware distribution / C2 |
| 4 | phishing | Phishing |
| 5 | adult | Adult / NSFW content |
| 6 | gambling | Gambling |
| 7 | social | Social media |
| 8 | dating | Dating sites |
| 9 | piracy | Piracy / copyright infringement |
| 10 | streaming | Video streaming (bandwidth) |
| 11 | games | Online gaming |
| 12 | fakenews | Fake news / misinformation |
| 13 | cryptojacking | Crypto mining scripts |
| 14-31 | reserved | Future categories |

**Format parsers:** Implement parsers for hosts format, domain list,
Adblock Plus syntax (`||domain^`), RPZ, and JSON. Convert all to the
internal `BlocklistEntry` representation.

**Daemon-mode behavior:**
- Per-source configurable refresh interval (default: daily, security lists
  more frequent)
- On fetch failure: serve stale data, exponential backoff (1min → 5min →
  15min → 1hr → 6hr), circuit breaker after N consecutive failures
- Schema validation: HTTP status, content-type, size sanity, header parse,
  first-N-lines smell test, entry count comparison (±10% variance)
- Background compilation to LMDB, atomic hot-swap
- On boot: load cached LMDB from disk, serve immediately, refresh in
  background. If no cache: block until critical lists (malware/phishing)
  loaded, serve non-critical as they arrive
- SIGHUP handler for manual reload trigger

### 4.4 DHCP server: built-in (replaces AdGuard Home DHCP + dnsmasq)

**Decision:** Include a DHCP server in dnshub using the `dhcproto` crate for
wire format and a custom lease state machine backed by SQLite.

**Why include DHCP:**
- AdGuard Home currently serves DHCP. Removing AdGuard without replacing DHCP
  would break the network.
- If dnshub owns the DHCP lease table, per-client policy gets client
  identification for free — no external lease file parsing, no dnsmasq
  dependency, no sync lag.
- The lease table is the authoritative source for IP → hostname → profile
  mapping. The ClientResolver reads directly from it.

**DHCP server scope:**
- IPv4 DHCP (port 67 UDP) — DHCPDISCOVER, OFFER, REQUEST, ACK, RELEASE, DECLINE
- IPv6 DHCPv6 (port 547 UDP) — SOLLICIT, ADVERTISE, REQUEST, REPLY, RENEW, REBIND
- IPv6 Router Advertisements (RA/SLAAC) — send RA on configured interfaces so
  devices can self-assign IPv6 addresses via SLAAC. This is the dominant IPv6
  allocation mode; stateful DHCPv6 alone is not sufficient.
- IP pool management with configurable ranges (multiple pools per interface)
- Static lease assignments (MAC → IP for v4, DUID → IPv6 for v6) for known devices
- Dynamic lease allocation from pool
- Lease persistence (SQLite) — survives restart
- Lease conflict detection (ping before offer)
- **MAC blocklist / lease refusal** — refuse to serve DHCP to specific MAC
  addresses. Devices on the blocklist get no IP. Configurable per-MAC or
  per-OUI (vendor prefix). Useful for banning unknown devices or specific hardware.
- **DDNS (dynamic DNS from DHCP)** — when a device gets a DHCP lease and
  includes a hostname (option 12), automatically create/update a DNS A/AAAA
  record in the local zone. When the lease expires or is released, remove the
  record. This is what makes local DNS "just work" — devices appear in DNS
  automatically without manual configuration. Both dnsmasq and AdGuard Home
  do this. The local zone is served by dnshub's own local zone handler.
- **Per-pool/per-subnet options** — different IP pools (guest, IoT, main) can
  have different DHCP options (DNS server, router, domain, NTP, etc.). This
  enables network segmentation where guest devices get a different DNS server
  or no NTP, IoT devices get a restricted DNS, etc.
- **Client classification** — auto-assign devices to pools/profiles based on:
  - Vendor class (option 60) — e.g., "Android-Phone" → phone profile
  - MAC OUI (first 3 octets) — e.g., IoT vendor prefix → IoT profile
  - User class (option 77) — explicit client classification
  This means new devices can be auto-profiled without manual static lease entry.
- **Arbitrary DHCP options** — configurable `option N = value` for any RFC 2132
  option, not just a hardcoded list. Supports both standard options and
  vendor-encapsulated options (option 43/125).
- **Standard DHCP options supported out of the box:**
  - Option 3 (router/gateway)
  - Option 6 (DNS server — points to dnshub)
  - Option 15 (domain name)
  - Option 28 (broadcast address)
  - Option 42 (NTP server)
  - Option 51 (lease time)
  - Option 60 (vendor class — read for classification)
  - Option 77 (user class — read for classification)
  - Option 119 (domain search list — v4)
  - Option 121 (classless static routes — tell clients about specific subnets)
  - Option 252 (WPAD — web proxy auto-discovery URL, for the proxy stack)
- **Lease time per-profile** — different profiles can specify different lease
  times. Kids devices get shorter leases (e.g., 1 hour) so policy changes take
  effect faster. Parents get standard 24h. IoT gets 7 days (stable).
- **Lease audit log** — track device join/leave events (DHCPACK, RELEASE,
  DECLINE, expiry) with timestamp, MAC, IP, hostname. Stored in SQLite,
  viewable in NextJS frontend. Security visibility for "what devices were on
  my network and when."
- **Rogue DHCP server detection** — periodically send DHCPDISCOVER probes.
  If a response comes from a non-dnshub IP, raise an alert (metric + log).
  Protects against misconfigured devices or malicious rogue DHCP servers.
- Per-lease metadata: hostname, MAC, vendor class (option 60), client identifier
- Device, device-user, and group tagging (each device user shoudl have up to many devices, each group should have up to many users or many devices, there shoudl be an unknown user and unknown group that is default). functionality so we can optionally assign multiple device per-user. This is to help manage rules by user and device, device should take precedence. And also to help people manage devices and users in UIs. Notes should be something we can add to devices and users to help describe things.

**DHCPv6-specific scope:**
- Stateful DHCPv6 (IA_NA — non-temporary addresses)
- Stateless DHCPv6 (DNS/domain info only, SLAAC handles addressing)
- Prefix delegation (IA_PD — for sub-routers that need a prefix)
- DHCPv6 options: DNS server (option 23), domain search list (option 24),
  NTP server (option 56), information refresh time (option 32)
- DDNS for DHCPv6 — create AAAA records in local zone from DHCPv6 leases
- RA configuration: prefix, preferred/valid lifetime, router lifetime,
  RDNSS (DNS server in RA), DNSSL (domain search list in RA)

**PXE/BOOTP/TFTP (in scope):**
- BOOTP (RFC 951, its own crate?) — static address assignment for diskless clients. BOOTP
  is a subset of DHCP; dnshub handles BOOTP requests by treating them as
  infinite-lease DHCP with a pre-configured MAC → IP → bootfile mapping.
- PXE (Preboot eXecution Environment, RFC 4578, its own crate?) — network boot support:
  - Option 60 = "PXEClient" — identifies PXE boot request
  - Option 93 (client architecture) — x86 BIOS, x86 UEFI, ARM UEFI, etc.
  - Option 94 (client network interface) — identifies NIC type
  - Option 97 (client machine ID) — UUID for unique identification
  - Option 66 (TFTP server name) — where to fetch boot image
  - Option 67 (bootfile name) — filename to boot from
  - Option 150 (TFTP server address) — IP of TFTP server
- Built-in TFTP server (read-only, possibly its own crate) — serves boot images, config files,
  and firmware to PXE clients. Uses `tokio` UDP with TFTP RFC 1350 protocol.
  Configurable root directory and allowlist of files.
- PXE proxy mode — dnshub can provide PXE boot info while another DHCP
  server handles address allocation (useful in mixed environments)
- Per-architecture bootfile mapping — different boot images for BIOS vs
  UEFI vs ARM, selected automatically from option 93
- iPXE chainloading support — option to chainload iPXE for HTTP-based boot
  (faster than TFTP, supports larger images and scripts)

**DHCP relay / multi-VLAN (in scope):**
- DHCP relay agent (RFC 1542 / RFC 8415 for v6) — dnshub can receive
  relayed DHCP requests (giaddr field set) from routers/switches on other
  VLANs and respond with leases for the appropriate subnet. This enables
  centralized DHCP for multi-VLAN networks without running dnshub on every
  VLAN.
- Relay handling:
  - Parse `giaddr` (gateway IP address) from relayed requests to determine
    the source VLAN/subnet
  - Select the appropriate IP pool based on `giaddr` or `link-address` (v6)
  - Send the response back to the relay agent (unicast to `giaddr`), not
    broadcast to the client
  - Support `Option 82` (Relay Agent Information) — parse circuit ID and
    remote ID sub-options for finer-grained client identification (e.g.,
    which physical switch port the client is on)
  - Use Option 82 for pool selection and profile assignment — e.g., a
    device on switch port 24 gets the guest profile automatically
- Multi-VLAN pool configuration — each VLAN/subnet gets its own pool with
  independent options, lease ranges, and default profiles
- DHCPv6 relay — handle Relay-Forw / Relay-Rel messages from relay agents
  on other VLANs, with `link-address` based pool selection
- Relay trust configuration — only accept relayed requests from configured
  trusted relay agent IPs (security: prevents rogue relays from exhausting
  pools or assigning profiles)

**DHCP failover/HA (pluggable, not implemented in v1):**
- v1 uses keepalived for VIP failover with separate local lease tables
  (SqliteLeaseStore). On failover, the standby dnshub re-assigns from its
  pool; clients may get a different IP. Acceptable for a homelab.
- The `LeaseStore` trait (see below) makes the storage backend pluggable.
  A future `FailoverLeaseStore` can wrap any `LeaseStore` and add
  inter-server lease synchronization (RFC 3074 for v4, RFC 8156 for v6)
  without changing the DHCP state machine, pool allocator, ClientResolver,
  or policy engine. The config schema for failover is already reserved.
- This also enables non-failover backends: `RedisLeaseStore` for
  multi-instance without full failover, `PostgresLeaseStore` for
  centralized lease storage in larger setups.

**Rust crates:**
- `dhcproto` — DHCP wire format encoding/decoding (maintained, used by
  cloud providers)
- `rusqlite` — SQLite for lease persistence (same DB as query log, different
  table)
- `async-trait` — for the `LeaseStore` trait that abstracts lease storage
- Custom lease state machine (no mature Rust DHCP server library exists)

**Lease storage abstraction (pluggable for future failover):**

All lease operations go through a `LeaseStore` trait. The default
implementation is `SqliteLeaseStore`. A future `FailoverLeaseStore` can
wrap any `LeaseStore` and add inter-server synchronization (RFC 3074/8156)
without changing the DHCP state machine, policy engine, or ClientResolver.

```rust
#[async_trait]
pub trait LeaseStore: Send + Sync {
    // v4 leases
    async fn get_lease_v4(&self, ip: &Ipv4Addr) -> Result<Option<DhcpLeaseV4>>;
    async fn get_lease_by_mac_v4(&self, mac: &MacAddr) -> Result<Option<DhcpLeaseV4>>;
```

**Why this matters:**
- `SqliteLeaseStore` — default, local only, what we build first
- `FailoverLeaseStore` — future wrapper that intercepts `on_lease_granted`/
  `on_lease_released` to sync state to a peer over TCP, implements
  `sync_from_peer` for recovery, and reports `partner_status` for the
  state machine. The DHCP state machine, pool allocator, ClientResolver,
  and policy engine don't change — only the storage backend swaps.
- The trait also enables other backends without failover: e.g., a future
  `RedisLeaseStore` for multi-instance without full failover protocol,
  or a `PostgresLeaseStore` for centralized lease storage in larger setups.

**Future LeaseStore backends (planned, not in v1):**

The `LeaseStore` trait is designed so that new backends can be added
without touching the DHCP state machine, pool allocator, ClientResolver,
policy engine, REST API, or frontend. Each backend is a crate that
implements the trait and is selected by config. Here's the roadmap:

| Backend | Status | Use case | What it adds |
|---------|--------|----------|--------------|
| `SqliteLeaseStore` | v1 (built first) | Single-instance homelab | Local persistence, zero external dependencies |
| `FailoverLeaseStore` | Phase 7 (future) | Two-node HA with lease continuity | Wraps any `LeaseStore` + syncs to peer over TCP. Implements RFC 3074 (v4) and RFC 8156 (v6) failover protocol. State machine: NORMAL, COMMUNICATIONS-INTERRUPTED, PARTNER-DOWN, RECOVER. Modes: load-balance (pool partitioning) and hot-standby (primary/secondary). On failover, standby has the full lease table — devices keep their IPs. |
| `RedisLeaseStore` | Future | Multi-instance without full RFC compliance | Multiple dnshub instances share lease state via Redis. No formal failover protocol — last-writer-wins with atomic Redis operations. Simpler than RFC 3074, good enough for 3+ instances where full failover protocol is overkill. Lease continuity depends on Redis persistence (RDB/AOF). |
| `PostgresLeaseStore` | Future | Centralized lease storage for larger setups | Leases stored in Postgres, queried by multiple dnshub instances. ACID transactions prevent lease conflicts. Useful when dnshub runs on multiple VLAN gateways but leases must be centrally managed. Adds Postgres as an external dependency — not suitable for standalone homelab deployments. |
| `EtcdLeaseStore` | Future | Cloud-native multi-instance | Leases in etcd with lease TTLs mapped to DHCP lease expiry. Watch API for real-time updates across instances. Good fit if dnshub is deployed in a Kubernetes environment where etcd is already present. |

**How a new backend wires in:**

1. Implement the `LeaseStore` trait in a new crate (e.g., `dnshub-lease-redis`)
2. Add the backend name to the config enum: `backend = "redis"`
3. Add backend-specific config section: `[dhcp.storage.redis]`
4. Register the backend in the `LeaseStoreFactory` at startup
5. Nothing else changes — the DHCP state machine, pool allocator,
   ClientResolver, policy engine, REST API, and frontend are all
   trait-bound and work with any `LeaseStore` implementation

```rust
// Factory pattern — selects backend at startup from config
pub enum LeaseStoreFactory {
    Sqlite(SqliteLeaseStoreConfig),
    Failover(FailoverLeaseStoreConfig),    // Phase 7
    Redis(RedisLeaseStoreConfig),          // future
    Postgres(PostgresLeaseStoreConfig),    // future
    Etcd(EtcdLeaseStoreConfig),            // future
}

impl LeaseStoreFactory {
    pub async fn build(&self) -> Box<dyn LeaseStore> {
        match self {
            Self::Sqlite(cfg) => Box::new(SqliteLeaseStore::new(cfg).await?),
            Self::Failover(cfg) => {
                // wraps an inner store (e.g., Sqlite) + adds peer sync
                let inner = SqliteLeaseStore::new(&cfg.inner).await?;
                Box::new(FailoverLeaseStore::wrap(inner, &cfg).await?)
            }
            Self::Redis(cfg) => Box::new(RedisLeaseStore::new(cfg).await?),
            Self::Postgres(cfg) => Box::new(PostgresLeaseStore::new(cfg).await?),
            Self::Etcd(cfg) => Box::new(EtcdLeaseStore::new(cfg).await?),
        }
    }
}
```

**What does NOT change when a new backend is added:**
- DHCP state machine (DISCOVER → OFFER → REQUEST → ACK → RELEASE → DECLINE)
- Pool allocator (find free IP, ping-before-offer, conflict detection)
- ClientResolver (IP → profile lookup via lease table)
- PolicyEngine (profile → allow/block decision)
- Client classification, MAC blocklist checks, DDNS, audit log
- PXE/BOOTP/TFTP, relay agent handling, Option 82
- All REST API endpoints (`/api/v1/dhcp/*`)
- All NextJS frontend code (DHCP views, lease table, audit log)
- Metrics and observability

**What DOES change:**
- One config line: `backend = "redis"` (or `"failover"`, `"postgres"`, etc.)
- Backend-specific config section (connection details, pool sizes, etc.)
- The `LeaseStoreFactory::build()` match arm for the new backend
- New crate dependency in `Cargo.toml`

**Docker deployment:** DHCP (v4 port 67 UDP, v6 port 547 UDP) requires L2
broadcast access, which Docker bridge networking doesn't provide. The
container must use **macvlan** networking — this gives dnshub its own MAC
address on the physical network, which is correct for a DHCP server. Host
network mode is an alternative but macvlan is preferred because it keeps
dnshub isolated while still on the LAN. The Ansible role will create the
macvlan network and attach the container to it. This is the same constraint
AdGuard Home has today.

### 4.5 Per-client policy: DHCP lease table + CIDR fallback

**Decision:** Use the internal DHCP lease table as the primary client
identifier, with CIDR range matching as fallback for non-DHCP clients
(static IPs, VPN clients).

**Client resolution order:**
1. DHCP static lease (MAC → IP → profile) — highest priority, explicit
2. DHCP dynamic lease (IP → hostname → profile via hostname_map)
3. Static IP → profile mapping (exact match, for VPN/static clients)
4. CIDR range → profile mapping (e.g., `192.168.10.0/24` → guest)
5. Default profile (catch-all for unmapped clients)

**Policy evaluation (per query):**
1. Resolve client IP → profile (ClientResolver)
2. Check custom_allowlist — if match, allow (skip blocklists)
3. Check custom_blocklist — if match, block
4. Check category blocklists — if domain's category bitmap intersects
   profile's blocked_categories, block
5. If `allowed_categories` contains "all", skip category check
6. Forward to upstream with profile-specific upstream selection

**Hot-reload:** SIGHUP reloads `policy.toml` without restart. Client
mappings and profiles swap atomically via `ArcSwap`.

### 4.6 Observability: hybrid (metrics crate + tracing + Jaeger)

**Decision:** Use the `metrics` ecosystem for Prometheus metrics, `tracing`
for structured JSON logs, and `tracing-opentelemetry` for Jaeger traces.
Defer all analytics to the existing Grafana stack.

**Why not pure OpenTelemetry:**
- OTel Rust metrics have known hot-path contention issues (RWLock on
  HashMap, weak→Arc upgrade in tracer)
- OTel Prometheus exporter crate was discontinued (unmaintained protobuf
  dependency)
- The `metrics` facade is allocation-free, battle-tested, and integrates
  directly with Prometheus scrape
- OTel traces are still Beta in Rust; `tracing-opentelemetry` bridges to
  Jaeger without needing the full OTel SDK

**Why not build a dashboard in the TS frontend:**
- Grafana already exists in the stack with Prometheus + Jaeger
- Reimplementing Grafana analytics is wasteful and fragments observability
- TS frontend should be config + status only, not analytics

```rust
    "source" => source_name, "status" => "success|failure|stale")
```

### 4.7 DoT/DoH server for LAN clients

**Decision:** Serve DoT (port 853) and DoH (port 443) to LAN clients using
hickory-server's built-in TLS and HTTPS listener support.

**Why:**
- Phones (iOS/Android) support private DNS via DoT — this lets phones on
  the LAN get encrypted DNS without per-app config
- Browsers that support DoH can use dnshub directly
- Encrypts DNS between client and dnshub (the hop that's on the LAN, before
  the query enters the upstream privacy chain)

**Implementation:**
- hickory-server supports DoT and DoH server endpoints natively
- TLS certificates: reuse existing ACME/Traefik certs (mounted into the
  container) or generate internal CA certs for LAN-only use
- DoH endpoint: `https://dns.levonk.com/dns-query` (RFC 8484 wire format)
- DoT endpoint: `dns.levonk.com:853`

**Config:**
```toml
[server]
listen = ["0.0.0.0:53", "[::]:53"]
protocol = ["udp", "tcp"]

[server.tls]
enabled = true
listen = ["0.0.0.0:853", "[::]:853"]
cert = "/etc/dnshub/tls/fullchain.pem"
key = "/etc/dnshub/tls/privkey.pem"

[server.doh]
enabled = true
listen = ["0.0.0.0:443", "[::]:443"]
path = "/dns-query"
cert = "/etc/dnshub/tls/fullchain.pem"
key = "/etc/dnshub/tls/privkey.pem"
```

**Note:** DoT/DoH clients are subject to the same per-client policy as
plain DNS clients — the source IP is extracted from the TLS connection,
and the ClientResolver maps it to a profile via the DHCP lease table.

### 4.8 Query logging: dual-path (SQLite + Loki)

**Decision:** Log every query to both an embedded SQLite database (for
live viewing in the NextJS frontend) and to structured JSON logs via
`tracing` (for long-term storage and Grafana correlation via Loki).

**Why both:**
- **SQLite** gives the NextJS frontend a queryable store without needing
  Loki API integration in the frontend. It's what Pi-hole and AdGuard Home
  use for their query logs. Fast for recent queries, bounded in size.
- **Loki** gives long-term retention and Grafana correlation (query logs
  alongside metrics, filter by time range + client + category). SQLite is
  a ring buffer (last N queries); Loki is the archive.

**SQLite query log schema:**
```sql
CREATE TABLE query_log (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp     INTEGER NOT NULL,    -- unix millis
    client_ip     TEXT NOT NULL,
    client_name   TEXT,                -- from DHCP lease table
    profile       TEXT,                -- policy profile used
    domain        TEXT NOT NULL,
    qtype         TEXT NOT NULL,       -- A, AAAA, MX, etc.
    response_code TEXT NOT NULL,       -- NOERROR, NXDOMAIN, SERVFAIL
    blocked       INTEGER NOT NULL,    -- 0 or 1
    block_category TEXT,               -- if blocked: which category
    block_source  TEXT,                -- if blocked: which list
    tier          INTEGER,             -- which upstream tier served it
    latency_ms    INTEGER,             -- resolution latency
    cached        INTEGER NOT NULL     -- 0 or 1
);

CREATE INDEX idx_query_log_timestamp ON query_log(timestamp);
CREATE INDEX idx_query_log_client ON query_log(client_ip);
CREATE INDEX idx_query_log_domain ON query_log(domain);
```

**Ring buffer behavior:**
- Default retention: 100,000 queries (~10-50MB depending on domain lengths)
- When full, oldest entries are deleted in batches of 1,000
- Configurable via `dnshub.toml`:
  ```toml
  [query_log]
  enabled = true
  max_entries = 100000
  retention_days = 7  -- alternative to max_entries: time-based cleanup
  ```

**NextJS frontend query log viewer:**
- Paginated table with columns: time, client, domain, type, status, blocked, category, tier, latency
- Filters: client, blocked-only, category, time range, domain search
- Real-time updates via WebSocket or polling (every 2s)
- Export to CSV (for sharing/debugging)

**Loki log format (structured JSON via tracing):**
```json
{
  "timestamp": "2026-08-10T12:34:56.789Z",
  "level": "info",
  "target": "dnshub::query_log",
  "fields": {
    "client_ip": "192.168.1.20",
    "client_name": "kids-tablet",
    "profile": "kids",
    "domain": "tiktok.com",
    "qtype": "A",
    "response_code": "NXDOMAIN",
    "blocked": true,
    "block_category": "social",
    "block_source": "stevenblack-social",
    "tier": null,
    "latency_ms": 0,
    "cached": false
  }
}
```

**Performance note:** SQLite writes are batched (every 100 queries or 1
second, whichever comes first) to minimize I/O on the query hot path. The
`tracing` log is async and non-blocking.

## 8. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| hickory-server API churn (0.25→0.26 broke Authority→ZoneHandler) | Medium | Pin to 0.26.x, implement against traits not concrete types |
| hickory-server "not for production" warning | Medium | Performance test thoroughly; fallback to hickory-proto only |
| UDP packet drops under load | Medium | SO_REUSEPORT tuning, socket count, buffer sizes (PR #3549) |
| LMDB C dependency | Low | heed provides safe Rust wrapper, LMDB is battle-tested |
| Blocklist source failures | Low | Serve stale, exponential backoff, circuit breaker |
| Per-client policy complexity | Low | Start with static IP mapping, add DHCP later |
| Migration breaks existing DNS | High | Deploy alongside, test with single client, gradual cutover |

## 10. Resolved Decisions

| Question | Decision | Rationale |
|----------|----------|-----------|
| DHCP server | **Include in dnshub (v4 + v6)** | AdGuard currently serves DHCP; removing it without replacement breaks the network. Owning the lease table gives per-client policy identification for free. DHCPv6 included from day one — new software in 2026 should support current standards. |
| DoT/DoH to LAN | **Include** | Phones support private DNS via DoT; browsers support DoH. Encrypts the client-to-dnshub hop on the LAN. |
| TLS cert source | **Default to Traefik/ACME, configurable** | Config points to cert/key file paths — doesn't care where they came from. Ansible role defaults to mounting Traefik's cert dir read-only. If someone wants internal CA, they change the paths. Zero extra work, maximum flexibility. |
| DHCP Docker network | **macvlan** | DHCP requires L2 broadcast access. Macvlan gives dnshub its own MAC on the physical network — correct for a DHCP server. Not a real question; there's no alternative that works for DHCP. |
| Query logging | **Dual-path: SQLite + Loki** | SQLite for live NextJS frontend viewing (individual events, ring buffer). Loki for long-term Grafana correlation (structured JSON). Prometheus is for metrics (aggregated stats), not event storage — using it for query logs would cause cardinality explosion. |
| Query log retention | **Both: max_entries + retention_days** | `max_entries = 100000` AND `retention_days = 7`, whichever triggers first. Bounded size + bounded time. |
| Frontend framework | **NextJS (static export)** | React ecosystem (Tremor, TanStack Table, shadcn/ui) is richer than SolidJS for dashboard/table components. Static export = no Node.js in production. |
| DHCP failover/HA | **Pluggable via LeaseStore trait, not in v1** | v1 uses keepalived + separate SqliteLeaseStore. LeaseStore trait makes storage backend swappable. Future backends: FailoverLeaseStore (RFC 3074/8156, Phase 7), RedisLeaseStore (multi-instance), PostgresLeaseStore (centralized), EtcdLeaseStore (cloud-native). Config schema for all backends reserved. See "Future LeaseStore backends" in section 4.4. |
| Service name | **dnshub** | User-confirmed. |
